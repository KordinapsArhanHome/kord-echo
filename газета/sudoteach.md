ORM или сырой SQL: что выбрать в Python

Разница по сути одна: кто пишет SQL — ты или библиотека.
Сырой SQL — отправляешь строку в драйвер, получаешь кортежи:

    &quot;SELECT id, email FROM users WHERE age &gt; &#036;1&quot;, 18)

SQLAlchemy — описываешь модель, SQL генерируется за тебя:

    select(User).where(User.age &gt; 18)).all()
На выходе объекты User, а не кортежи. В повседневной работе это и есть главное отличие.

Что даёт ORM
— Один источник правды: модель = таблица. Поле меняешь в одном месте.— Alembic генерит миграции по диффу моделей.— Связи: user.posts вместо ручного JOIN и разбора плоского результата.— Автодополнение и mypy ловят опечатку в имени колонки до прода.— Переносимость: SQLite в тестах, PostgreSQL в бою.

Чем ORM бьёт по рукам
— N+1. Цикл по user.posts на 500 пользователей = 501 запрос. Лечится selectinload, но сначала надо заметить.— Сгенерированный SQL бывает далёк от того, что написал бы руками. EXPLAIN обязателен.— Оконные функции, CTE, рекурсия — на ORM превращаются в шифр.— Маппинг в объекты стоит времени и памяти. На 200к строк это уже заметно.— Знание SQL ORM не отменяет, а добавляет сверху ещё один слой абстракции.

Когда сырой SQL
— Тяжёлая аналитика и отчёты.— Bulk-операции, COPY, массовые UPDATE.— Специфика СУБД: JSONB-операторы, полнотекст, партиции.— Разовые скрипты и миграции данных.

Про инъекции
Расхожий миф, что ORM защищает, а сырой SQL нет. Защищает параметризация. WHERE id = :id безопасно и там, и там. f-string опасен и там, и там.

Практика
CRUD, админка, бизнес-логика — ORM. Узкие места — сырой SQL прямо через session.execute(text(...)). Выбирать что-то одно раз и навсегда смысла нет.

 Что такое JWT и как он работает в FastAPI?

JWT (JSON Web Token) — это компактный цифровой «пропуск» для пользователя. Вместо того чтобы хранить активную сессию юзера в базе данных, сервер выдает клиенту защищенный токен, в котором уже зашита вся необходимая информация (например, ID пользователя и срок его действия).
Сам токен выглядит как длинная строка из трех частей, разделенных точками: Header.Payload.Signature (Заголовок, Данные, Подпись).



🌟

 Как выглядит процесс в FastAPI:


1️⃣
 Логин: Пользователь отправляет логин и пароль на эндпоинт авторизации.

2️⃣
 Выдача токена: FastAPI сверяет данные. Если всё верно, он генерирует JWT, подписывает его вашим секретным ключом (SECRET_KEY) и возвращает клиенту.

3️⃣
 Запрос к API: Клиент хочет получить доступ к защищенному маршруту. Он прикрепляет полученный токен к каждому запросу в заголовке Authorization: Bearer &lt;токен&gt;.

4️⃣
 Проверка (Валидация): В FastAPI обычно используется встроенный инструмент OAuth2PasswordBearer через систему зависимостей (Depends). Этот механизм автоматически достает токен из заголовка и проверяет его криптографическую подпись, а также срок годности.

5️⃣
 Ответ: Если токен валидный, FastAPI разрешает доступ к функции. Если подпись не совпадает или токен просрочен — отдаст ошибку 401 Unauthorized.

 Что такое CI/CD и почему без него на продакшене никуда?

Если вы до сих пор обновляете код на сервере вручную через FTP или git pull прямо на прод — этот пост для вас. Давайте разберем базовую базу современной разработки.

CI/CD (Continuous Integration / Continuous Delivery) — это автоматизированный конвейер (пайплайн), который берет ваш свежий код, проверяет его и доставляет до пользователя. Без рутины и человеческого фактора.
Разложим по полочкам:


🧩
 1. CI — Непрерывная интеграция (Continuous Integration)
Вы написали фичу и закоммитили её. В этот момент автоматически запускается CI-пайплайн:
• Код собирается в единое целое.• Запускаются линтеры (проверка стиля кода) и автотесты (юнит, интеграционные). • Зачем? Чтобы поймать баги до того, как они попадут в общую ветку и сломают проект коллегам.


🚚
 2. CD — Непрерывная доставка / развертывание (Continuous Delivery / Deployment)
Когда тесты пройдены, код автоматически (или по нажатию одной кнопки) отправляется на сервера:
• Создается продакшен-сборка (например, Docker-образ).• Код деплоится на стейджинг или сразу на прод.• Зачем? Чтобы новые фичи долетали до пользователей за минуты, а не копились месяцами до &quot;большого четвергового релиза&quot;.


🪵
 Почему это критично на продакшене?
• Минимум человеческого фактора. Компьютер не забудет обновить переменные окружения и не пропустит упавший тест из-за усталости.• Быстрый Time-to-Market. Нашли баг или придумали крутую фичу? Она на проде уже через 5-10 минут.• Легкий откат (Rollback). Если на проде что-то пошло не так, одной кнопкой можно вернуть предыдущую стабильную версию сборки.• Спокойный сон команды. Автоматизация рутины освобождает время разработчиков для реальных задач, а не для борьбы с серверами.

Итог: CI/CD — это не роскошь для корпораций, это стандарт качества и безопасности для любого коммерческого проекта.
А как у вас настроен деплой? Всё автоматизировано или по старинке «в продакшен по SSH»?
